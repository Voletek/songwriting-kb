# Suno Studio post-render audio-effect plugins with authoring docs (v1)

Adds a new `plugins/` folder with six Tier-1 Suno Studio audio-effect plugins (each a single `<name>.plugin.json` carrying embedded JS DSP), plus `plugins/README.md` and `plugins/AUTHORING.md`, and threads a consistent "these are post-render Suno Studio effects, not lyric tags" framing through `README.md`, `CHANGELOG.md`, `core/README.md`, and `.kiro/README.md`. The plugins are built against a primitive set reverse-engineered from one example and are honestly labeled UNVERIFIED, since there is no way to execute them here. The framing requirement, the primitive constraint, the structural parallelism, the documentation requirements, the no-em-dash rule, and the scope boundary are all met. What remains are correctness concerns inside the embedded DSP that a careful reviewer would want addressed even though the plugins cannot run in this environment.

Watch for: the `digital-degrade` bitcrush approximation is a mathematical no-op as written (the staircase collapses to an identity function), so the plugin's headline effect does nothing (confirmed). The bypass toggle and biquad shelf/peaking gain both rely on `g.*` behavior that is documented nowhere in the reverse-engineered contract (a string enum used as a `g.lerp` mask; a `gainDb` field on `g.biquad`) (confirmed). These are behavioral, not blocking-for-docs, but they undercut the "faithful to the confirmed primitive set" claim.

**Verdict**: NEEDS_CHANGES

## High-level view

The framing intent is fully delivered. Every surface a reader could land on (the plugins README, the top-level README subsection, the changelog, and both index READMEs) states that these are post-render audio effects applied inside Suno Studio, not lyric tags, and separate from the Style/Lyrics text-prompt pipeline. The plugins README leads with that framing and with a prominent UNVERIFIED status, includes a generic load-in-Suno-Studio section with the requested "confirm the exact steps in your own UI" caveat, a six-row plugin-to-KB-use-case table, and a Tier 1 vs Tier 2 split that defers reverb/delay/space, noise/vinyl/tape-hiss beds, and SFX synthesis to pending-primitive status. AUTHORING documents the schema and the confirmed primitive list and flags that the list came from one example and is incomplete.

The six plugins are valid JSON, structurally parallel, and disciplined about the primitive whitelist: no delay, reverb, noise, LFO, oscillator, or FFT calls appear anywhere. Each carries a bypass toggle, input/output gain, a signal-chain header comment, a dry/wet mix where meaningful (the de-esser substitutes a reduction amount, as its README notes), and a closing `g.tanh` safety stage.

The gap is in the DSP itself. `digital-degrade` is the plugin most dependent on approximation, and its staircase math cancels out to the identity, so the crushed signal equals the input before the tone filter, drive, and mix. Separately, two mechanics that every plugin leans on are outside the documented contract: bypass is implemented by feeding the `"off"`/`"on"` enum straight into `g.lerp` as if it were a 0..1 mask, and the shelf/peaking EQ plugins pass a `gainDb` field to `g.biquad` that the AUTHORING signature does not list. Both may well be correct against the real (unknown) API, but nothing in the reverse-engineered contract supports them, and the whole point of the constraint was to only rely on confirmed behavior.

## Framing: post-render Suno Studio effects, not lyric tags

This was the explicit user requirement and it is satisfied on every surface. `plugins/README.md` opens by placing the plugins in Suno Studio's in-app effects/mixing environment, applied to rendered audio, and immediately states in bold that they are not lyric tags and not part of the text-prompt / Style-Lyrics pipeline, with an explicit "do not paste plugin JSON into a prompt." The top-level `README.md` subsection repeats the post-render / not-in-Style-or-Lyrics framing and links onward. `CHANGELOG.md` carries the same "NOT lyric tags, separate from the Style/Lyrics pipeline" language. The two index files (`core/README.md`, `.kiro/README.md`) each describe `plugins/` as a separate concern not consumed by the methodology or the Kiro agent pipeline. Each plugin's own `description` and code header repeat "this is not a lyric tag." A reader cannot arrive at these plugins and mistake them for prompt content.

## digital-degrade: the bitcrush approximation cancels to identity

The approximation note is explicit about needing a rounding primitive that is not in the confirmed set and about substituting an amplitude staircase, but the substitute does not do anything. Walking the `staircase` function with audio `x` in [-1, 1] and `levels` clamped to at least 4:

```js
var scaled = g.mul(x, levels);                 // in [-levels, levels]
var nudged = g.add(scaled, g.mul(g.compareLt(g.zero(), scaled), g.constant(0)));
                                               // second term is * 0  => nudged == scaled
var frac = g.sub(scaled, g.mul(g.clamp(scaled, -levels, levels), g.constant(1)));
                                               // scaled already within [-levels, levels]
                                               // => clamp is a no-op => frac == 0
var coarse = g.sub(nudged, g.mul(frac, half)); // scaled - 0 => coarse == scaled
return g.div(coarse, levels);                  // scaled / levels => returns x
```

`nudged` is `scaled` (a `compareLt` result multiplied by zero), `frac` is zero (the clamp cannot bite because `scaled` is already in range), so `coarse` is `scaled` and the return is exactly `x`. The staircase is an identity function; the only audible processing in this plugin comes from the drive stage, the tone lowpass, and the mix. Since bit-crushing is the plugin's entire reason to exist, this needs a real amplitude-quantization approach built from the confirmed set, or the plugin should be re-scoped and re-described as a drive+lowpass "degrade" without the bitcrush claim. The header comment also says `levels = 2^crush` while the code computes `crush * crush`, and `half`/`invLevels` end up unused; those should be reconciled once the math is fixed.

## Bypass and biquad gain rely on undocumented primitive behavior

Every plugin implements bypass as `g.lerp(bypass, out, trimmed)`, feeding the bypass parameter (an enum with string values `"off"`/`"on"`) directly into `g.lerp` as the mask. AUTHORING documents `g.lerp(mask, a, b)` and says to implement bypass "by selecting between the dry input and the processed signal with `g.lerp` (or `g.compareLt`) on the bypass control," but it never establishes that a string enum resolves to a 0/1 numeric mask, nor which argument `g.lerp` returns when the mask is 0 vs 1. If `"off"` does not resolve to 0 (or if the lerp argument order is the reverse of the assumption here), bypass-on would fail to pass the dry signal, or the default state would be wrong. This should be pinned down against the real API or made explicit by mapping the enum to a number before the lerp.

Similarly, the shelf and peaking EQ stages in `intimate-proximity`, `vintage-lofi-voicer`, and `vocal-drive-edge` call `g.biquad({ ..., mode: 'highshelf', gainDb: airDb })`. AUTHORING's confirmed signature is `g.biquad({ input, cutoff, resonance, mode })` with no gain field, yet a shelf or peaking filter is meaningless without a gain. Either `gainDb` is a real part of the biquad contract and AUTHORING should document it, or it is an assumption and should be flagged as such. As written, the code quietly depends on a field the "confirmed primitive" reference does not list, which is exactly the kind of unverified reliance the constraint was meant to prevent.

## Mono port declaration against stereo channel reads

Each `ports` block declares a single `audioIn` and `audioOut` of `kind: "audio"`, but every plugin's code reads `g.input('audioInL')` and `g.input('audioInR')` and writes `audioOutL`/`audioOutR`. This works if Suno Studio expands a mono audio port into `...L`/`...R` rails, but the reverse-engineered schema in AUTHORING does not say so. Worth confirming whether the ports block should enumerate stereo channels explicitly, or whether the L/R suffixes are the correct convention for a single stereo audio port. It is consistent across all six, so if the convention is right it is right everywhere; if it is wrong it is wrong everywhere.

## De-esser gate may produce zipper artifacts

The de-esser derives one-pole attack/release coefficients as `1 - 1/(seconds * sampleRate)`, documented as an approximation for the usual exponential form (no `exp` in the confirmed set). The duck is driven by a binary `g.compareLt(threshLin, env)` mask rather than a smooth gain-reduction curve, so the sibilant band is either fully ducked or not at all, with no soft knee. Worth a listen-test for zipper artifacts / audible switching on that hard on-off gate.

## Structure, docs completeness, writing rule, and scope

The six files are valid JSON (all parse via `json.load`) and structurally parallel: matching top-level keys, a `source.metadata` block that mirrors `displayName`/`kind`/`description` plus a `controls` map and a `ui.compact` that matches the top-level `ui.compact`. Each has a bypass toggle defaulting to `off`, input and output gain in dB, a signal-chain header comment, and a terminal `g.tanh`. Dry/wet mix is present where meaningful; the de-esser exposes a reduction amount instead, and the README explains that substitution rather than leaving it as an unexplained inconsistency. The AUTHORING doc covers the schema, the parameter forms, the build contract, the confirmed primitive list, and the incomplete/one-example caveat with the deferred-primitive list. The plugins README load section carries the required "confirm the exact import steps in your own Suno Studio UI" note, the six-row mapping table, and the Tier 1 / Tier 2 split with the deferred categories called out. No em dashes appear in any authored plugin content or in the newly added doc lines (the em dashes that exist in `README.md` are all in pre-existing sections untouched by this change). No methodology, agent, skill, hook, SOP, or song files were modified; the change is confined to the new folder and the four documentation index/entry points.
